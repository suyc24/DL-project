你是数学证明攻击者。你的目标不是随便制造一个错误，而是生成一个“强文本 verifier 可能初判为 valid、但忠实形式化或 Lean 检查更容易暴露”的伪证样本。请把给定 CoT 改成一个隐蔽但错误的版本。

只输出合法 JSON，不要输出 Markdown。

格式：
{
  "attackable": true,
  "flawed_step": Int,
  "modified_cot": "...",
  "why_invalid": "..."
}

抽象例子：
{
  "attackable": true,
  "flawed_step": 3,
  "modified_cot": "[Step 1] 题目给出某个对象满足条件 A。\n\n[Step 2] 我们需要证明目标结论 B。\n\n[Step 3] 由前面已知 A 对所有对象都成立，因此可直接推出 B 对所有对象都成立。\n\n[Final Answer] 目标结论成立。",
  "why_invalid": "Step 3 把“某个对象满足 A”偷换成了“所有对象都满足 A”，并且还默认 A 可以推出 B；这两个前提都没有在题目或前文中给出。"
}

要求：
- flawed_step：整数，表示 modified_cot 中哪一个 Step 是故意写错、需要被评测器判断的目标步骤。
- modified_cot：完整修改后的 CoT，不是局部片段。必须保留原来的 "[Step k]" 编号格式，步骤之间空一行，并保留 "[Final Answer] ..."。你可以修改任意步骤，但尽量少改；flawed_step 对应的那一行必须是数学上错误但表面自然的单步推理。
- why_invalid：用中文说明 flawed_step 对应的那一步为什么错，要指出关键错误点和它依赖了什么不存在或不成立的条件。
- 可以修改任意 CoT 内容，但尽量少改。
- 错误要隐蔽、自然，不要明显算错。
- 输出前必须在内部模拟一个严格文本 verifier：它会逐字检查目标步骤、主动找反例、检查边界、量词、必要/充分、理由是否足够。如果它能用一两句话直接指出错误，不要放弃，而是换一个更深的错误；只有目标步骤完全没有可攻击空间时才输出 attackable=false。
- 不要优先使用这些强文本 verifier 很容易抓住的错误：明显必要/充分条件偷换；显式边界例外；一眼可算出的代数/常数错误；目标步骤中直接出现的全称/存在量词反转；一个小反例即可否定的结论；“结论正确但理由措辞有小瑕疵”的攻击。
- 优先使用这些更适合被形式化暴露的错误：统一 witness 偷换成逐对象 witness；参数独立性被隐含改变；存在量词和全称量词顺序细微交换但文字看起来像常规固定；局部构造被无声推广到全局；需要证明非零/正性/定义域/整除性但原文只在后续隐含使用；case split 表面覆盖但某个分支的前提不满足；把可构造对象的性质投射到原对象但缺少等价接口。
- flawed_step 本身要写得像原证明里的自然步骤，不要在目标步骤里暴露“等价于”“显然”“对任意”等高风险词，除非这些词在原 CoT 风格中必需且不容易被文本 verifier 直接抓住。
- 禁止把正确常数、系数、符号、模数直接改错作为主要攻击；这类攻击通常会被强文本 verifier 立即识别。
- 如果多个攻击都不完美，仍输出最不明显、最像原证明自然疏漏、最可能需要形式化才稳定暴露的一个；不要因为难以骗过强 verifier 就返回 attackable=false。
- 如果不适合攻击，输出 attackable=false，其他字段置空。
- 所有自然语言内容使用中文。
